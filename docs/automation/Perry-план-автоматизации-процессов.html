1. Коротко

Идея в одной фразе. Берём Perry так, как будто это работающий интернет-магазин, находим, где люди делают руками одно и то же, и отдаём это воркфлоу в n8n, которые ходят в API Perry, «Новую почту», Telegram и Google Sheets. Над ними стоит AI-агент-оркестратор: он решает, какой воркфлоу запустить, а важные действия (деньги, публикации, письма клиентам) отдаёт человеку на одобрение.
Что уже есть ✅ Работающий магазин: витрина React, Product API на .NET 8 + PostgreSQL, вход через отдельный Auth-сервис, админка, мобильное приложение Expo. 15 автотестов, ~194 демо-товара. См. Что за проект
Сколько ручной работы ⚠️ ≈ 473 ч/мес при допущении «50 заказов в день» (карта процессов)
Сколько уберём ⚠️ ≈ 362 ч/мес после 12 недель внедрения ≈ 72 500 грн/мес при примерной ставке 200 грн/ч (эффект)
Цель вакансии ✅ 250 сэкономленных часов в месяц минимум, около 500 ч/мес к концу первых 3 месяцев (вакансия)
Честный вывод 250 ч/мес достигаем на 2-м месяце. 500 ч/мес при 50 заказах в день не достигаем: нужно ≈ 90 заказов в день или ещё один поток (например, финансы). Расчёт в разделе 14
Первые шаги для портфолио 3 воркфлоу, которые можно собрать в локальном n8n против локального Perry API за выходные: KPI-дайджест, бот «где мой заказ», AI-описание товара с одобрением
Чего не хватает в коде исходящих вебхуков, сервисного токена для n8n, точечного обновления остатков, полей доставки в заказе. Список в разделе 13

Вакансия (проверено 06.10.2026 на work.ua/jobs/8532037) ✅:

  • Должность: AI Automation, Process Optimization Specialist, компания Race Expert (raceexpert.com.ua), розничная торговля, 10–50 сотрудников, удалённо, полная занятость, 5/2, уровень Middle.
  • Зарплата: 28 000 – 65 000 грн «после всех вычетов», ставка + бонус. Рассматривают бонусы, привязанные к реальному экономическому эффекту.
  • Задачи (дословно по смыслу): самому находить процессы для автоматизации, раскладывать работу команд на операции, описывать будущую логику, собирать и запускать автоматизации (AI, API, Make, n8n), следить, чтобы ими реально пользовались, и считать экономию времени и денег каждого решения.
  • С чего начнут: первым большим направлением названы бухгалтерия и финансовые процессы. Дальше: контент-маркетинг, продажи, операционные процессы, закупки, склад, аналитика. ⚠️ Уточнение: пользователь говорил про «складскую логистику и маркетинг», а в тексте вакансии первыми стоят финансы, склад и маркетинг идут следом.
  • Ориентир: минимум 250 сэкономленных рабочих часов в месяц; за первые 3 месяца выйти примерно на 500 сэкономленных часов в месяц.
  • Плюсом будет: n8n, Make, AI-модели и AI-агенты, API и webhooks, CRM, ClickUp, 1С или другие учётные системы, e-commerce. Глубокая разработка не обязательна.
  • Формат: украинский язык обязателен, подчинение Project Manager, своей команды нет.
  • Главная фраза для портфолио: «Нам не подойдёт человек, который говорит: "Я сделал классного AI-бота", но не может ответить, что этот бот дал бизнесу в часах или деньгах». Поэтому в этом документе у каждого шага есть часы и гривны.

❓ Внутренние процессы Race Expert нам неизвестны, мы их не описываем. Все процессы ниже относятся к Perry как к условному работающему магазину. Где в коде Perry чего-то нет, стоит пометка допущение.

2. Что за проект

2.1. Perry одной картинкой

Perry (PERRY) — дипломный командный проект IT STEP: интернет-магазин-маркетплейс, «наша версия Амазона». Покупатель листает каталог с фильтрами, кладёт товары в корзину (даже без входа), оформляет заказ, следит за статусом, пишет отзывы и ведёт список избранного (wishlist). Администратор управляет товарами, категориями, отзывами, заказами и пользователями.

Репозитории: Teslyar75/My_Amazon2 (основной, его Сергей называет «Tesla 75 / Amazon 2») и командное зеркало ITSTEP-PERRY/Back_end_for_our_poroject. На ноутбуке Сергея проект лежит в D:\Perry (в этом плане его не трогаем). Клон на коммите bcaec5f лежит в /workspace/perry.

flowchart LR
  B["Браузер<br/>витрина :3000"] --> SPA["React + Vite SPA"]
  M["Мобильное Expo<br/>:8081"] --> API
  SPA -->|"вход, JWT"| AUTH["Auth Service<br/>Azure, Влад"]
  SPA -->|"Bearer JWT<br/>/api/*"| API["Product API :5272<br/>зона Сергея"]
  SPA -->|"Admin JWT"| ADM["Admin Service<br/>пользователи"]
  API -->|"internal/auth/token<br/>internal/users/id"| AUTH
  API --> DB[("PostgreSQL<br/>Product DB")]
  API -->|"SMTP письма"| MAIL["Email покупателю"]
  N8N["n8n + AI-агент<br/>будущее"] -.->|"HTTP Request<br/>сервисный токен"| API
  API -.->|"вебхуки событий<br/>нужно добавить"| N8N
  N8N -.-> EXT["Новая почта · Telegram<br/>Google Sheets · OpenAI"]

Как ходит запрос (кратко). Покупатель входит через Auth и получает JWT. Витрина шлёт его в Product API в заголовке Authorization: Bearer …. Product API сам проверяет подпись токена (JwtAuthenticationService.cs) и берёт из него UserId (AuthClaims.cs). Своей таблицы пользователей в Product DB нет: email и имя Product API при необходимости спрашивает у Auth по внутреннему каналу (AuthInternalClient.cs). Этот же приём, «сервис получает свой токен», нужен и для n8n: см. сервисный токен, API-2.

Что важно для автоматизации ✅:

  • уже есть письма покупателю при заказе и смене статуса (OrderService.cs, строки 387–403). Значит, точки «заказ создан» и «статус изменился» в коде уже есть, к ним легко прицепить вебхук (API-1);
  • при заказе остаток списывается и товар уходит в OutOfStock на нуле (строки 344–351);
  • есть подписка «сообщить о поступлении», но письмо о поступлении никто не отправляет: поле NotifiedAtUtc нигде в коде не заполняется (StockNotifyRequest.cs). Готовая быстрая победа для А2;
  • есть /api/health для мониторинга (Program.cs) и dev-вход администратора для локальных демо (DevAdminAuthController.cs), его используют портфолио-воркфлоу.

4. Части проекта подробно

Для каждой части: что это, как выглядит, что делает, какой API, где её касается автоматизация.

4.1. Витрина (frontend, React + Vite)

  • Что это: одностраничное приложение (SPA) на React 19, макет по Figma. Запуск — localhost:3000, запросы /api проксируются на Product API :5272 (README).
  • Как выглядит: рис. 1–10: синяя шапка с поиском, светлые карточки, салатовые кнопки.
  • Что делает: маршруты главной, каталога, товара, корзины, checkout, кабинета, legal и 404 (router.tsx); админка живёт в том же приложении под /admin (строки 101–114).
  • API: все вызовы собраны в одном файле frontend/src/api/index.ts.
  • Автоматизация: витрину почти не меняем. Добавляем телефон и отделение НП в checkout (API-5), трекинг-номер в «Мои заказы» (А5), позже виджет чата с ботом (Г1).

4.2. Product API (зона Сергея)

  • Что это: REST-сервис на ASP.NET Core 8, три слоя: Perry.Api (контроллеры), Perry.Domain (сущности), Perry.Infrastructure (БД, сервисы). Swagger на /swagger (Program.cs).
  • Как выглядит: экрана нет, его «лицо» — Swagger. Данные видны на всех экранах витрины.
  • Что делает: каталог с фильтрами, карточка, корзина гостя и пользователя, checkout со списанием остатков, статусы заказа с письмами, отзывы с модерацией, wishlist, подписка «сообщить о поступлении», health-check.
  • Сущности: товар с SKU, ценой, старой ценой, остатком и статусом (Product.cs); заказ с номером #AT456BB, суммой, адресом, оплатой (Order.cs); позиция заказа со «снимком» цены и названия (OrderItem.cs); отзыв с оценкой 1–5 и флагом IsApproved (ProductReview.cs).
  • Права: политики AdminAccess и SellerAccess по роли из JWT (Program.cs).
  • Автоматизация: главная точка интеграции. Все потоки А–Д читают данные отсюда, а раздел 13 перечисляет, что сюда нужно добавить.

4.3. Auth-сервис (зона Влада)

  • Что это: отдельный сервис в Azure: регистрация, вход, подтверждение email кодом, сброс пароля, выдача JWT (HS256, общий секрет с Product API).
  • Как выглядит: рис. 11 и кадры регистрации и кода.
  • Что делает для Product API: выдаёт сервисный токен по POST /internal/auth/token (имя сервиса + секрет из env) и отдаёт данные пользователя по GET /internal/users/{id} (AuthInternalClient.cs).
  • Автоматизация: просим у Влада отдельный сервисный аккаунт n8n-automation с узкими правами (API-2, вопрос 3).

4.4. Админка (UI + Admin Service)

  • Что это: раздел /admin той же витрины (frontend/src/pages/admin) плюс отдельный Admin Service для пользователей. Бэкенд админки — зона другого участника команды.
  • Как выглядит: рис. 12–18: светлая шапка, таблица слева, детали справа.
  • Что делает: товары, категории, модерация отзывов, заказы со сменой статуса, пользователи с ролями. Поток админских заказов на защите показан диаграммой 16-admin-orders-flow: GET /api/orders/admin → PUT /orders/{id}/status → UpdatedAtUtc.
  • Автоматизация: админка становится местом, где человек одобряет то, что подготовил агент: черновики товаров, ответы на отзывы, закупки (раздел 11). Пока окна одобрений нет, роль играет Telegram с кнопками.

4.5. Мобильное приложение (Expo)

  • Что это: React Native на Expo, экраны Home, Products, Product, Cart, Checkout, Orders, Order details, Account, Login, Register (mobile/src/screens). Токен хранится в expo-secure-store (package.json).
  • Как выглядит: рис. 19.
  • Автоматизация: пользуется тем же API, поэтому получает плоды потоков А–Д бесплатно. ❓ Push-уведомления — после того как появятся вебхуки (API-1).

5. Админка: что неудобно и что автоматизировать

Админка Perry аккуратная и рабочая, но сделана как «таблица + карточка справа»: каждое действие — руками, по одному объекту. Для дипломного проекта это нормально. Для магазина на 50 заказов в день ⚠️ это и есть те самые часы, которые ищет вакансия. Ниже разбор по каждому экрану: сначала что неудобно (✅ видно на скрине или в коде), потом что поправить в интерфейсе (дёшево, без AI) и что отдать автоматизации.

Шаги автоматизации

А1. Синхронизация остатков и цен с поставщиками

Экраны: товары, создание товара · модуль: Product API · нужно: API-3, API-4

  1. Schedule Trigger — раз в час (или Gmail Trigger на письмо с прайсом).
  2. HTTP Request / Read Binary File / Gmail — забрать файл прайса поставщика.
  3. Extract from File — XLSX или CSV в строки.
  4. Code — привести к общему виду {sku, qty, purchasePrice}; разные поставщики называют колонки по-разному, правила лежат в Data table n8n.
  5. HTTP Request → GET /api/admin/stock?skus=… (API-3) — текущие остатки Perry.
  6. Compare Datasets — найти расхождения по SKU.
  7. IF — расхождение больше 30 % или цена изменилась больше чем на 10 %? → в Telegram «Send and Wait for Response» на одобрение человеку (HITL). Мелкие расхождения проходят сами.
  8. HTTP Request → PATCH /api/admin/stock/bulk (API-3) с ключом идемпотентности (API-9).
  9. Google Sheets — строка в журнал: сколько SKU обновлено, кем, когда.

Важно ✅: сейчас обновить остаток можно только через PUT /api/products/{id}, который перезаписывает фото, характеристики и about целиком (ProductsController.cs). А GET /api/products/update/{id} отдаёт характеристики без флага IsFilterable (строки 221–223), и при обратной отправке флаг станет false (строка 685, по умолчанию IsFilterable = false, строка 528). Фильтры каталога (рис. 2) после такой синхронизации сломаются. Поэтому для А1 обязателен отдельный эндпоинт остатков (API-3).

А2. Низкие остатки, черновик закупки и «снова в наличии»

  2. HTTP Request → остатки (API-3) и продажи за 14 дней (GET /api/orders/admin?fromUtc=…, код).
  3. Code — «дней до нуля» = остаток ÷ средние продажи в день; порог 7 дней ⚠️.
  4. OpenAI (или AI Agent) — собрать черновик письма поставщику: таблица SKU и количество, вежливый текст на украинском.
  5. Telegram «Send and Wait for Response» — менеджер закупок жмёт «Отправить» или «Исправить».
  6. Gmail — письмо поставщику после одобрения.
  7. Ветка «снова в наличии»: вебхук product.back_in_stock → HTTP Request GET /api/admin/stock-notify/pending?productId=… (API-6) → Send Email каждому подписчику → PATCH …/notified. Сегодня подписка сохраняется (StockNotifyController.cs), а письма о поступлении нет совсем (G4).

А3. Сборочный лист по заказу

  4. Google Sheets — строка в лист «Сборка на сегодня»; HTML + Convert to File — PDF для печати.

10. Система автоматизации целиком

Потоки А–Д — это не 22 отдельных «робота», а одна система из пяти слоёв. Если строить их по отдельности, через полгода получится зоопарк: у каждого воркфлоу свой токен, свои копии справочников, ошибки никто не видит. Поэтому сначала договариваемся об общей архитектуре.

10.1. Пять слоёв

Слой Что это Из чего состоит Где описано
1. Источники событий всё, что «происходит» в магазине Product API (заказ, статус, остаток, отзыв, товар), Telegram (сообщения клиентов), почта (прайсы), расписание API-1, Г1, А1
2. Шина событий единая точка входа один Webhook n8n /perry-events с проверкой подписи HMAC → Switch по типу события → Execute Workflow нужного потока 10.2
3. Исполнители воркфлоу n8n, по одному на процесс А1…Д2, каждый — маленький под-воркфлоу с одной задачей потоки
4. AI-слой думает, но ничего не делает сам AI-оркестратор выбирает, что запустить; специализированные агенты (контент, маркетинг, поддержка, модерация) пишут тексты и метки раздел 11
5. Контроль человек и журнал одобрения в Telegram (позже в админке), журнал действий, алерты об ошибках, метрики сэкономленных часов 11.2, 11.3, Д2

Общие правила для всех воркфлоу:

  • Один сервисный токен Perry на всю систему, хранится в Credentials n8n, обновляется сам (API-2).
  • Справочники в одном месте: Data table n8n (характеристики, пороги, правила поставщиков).
  • Каждая запись в Perry — с ключом идемпотентности (API-9), чтобы повторный запуск не создал вторую ТТН.
  • Каждый воркфлоу пишет строку в журнал: что сделал, сколько минут ручной работы это заменило. Из журнала считаются часы и деньги.
  • Всё, что касается денег, клиентов и публикаций, проходит через человека (11.2).

11. AI-агенты и оркестрация

11.1. Оркестратор над воркфлоу

Оркестратор (глоссарий) — это AI-агент-диспетчер, такой же по смыслу, как Grok Bot у Сергея: он получает задачу на обычном языке («почему вчера мало заказов?», «оформи возврат по #AT456BB», «подготовь посты про новые кроссовки»), сам выбирает, какие воркфлоу вызвать, собирает результат и отвечает.

Как это собрать в n8n:

  1. Telegram Trigger (чат сотрудников) или Chat Trigger (окно в админке, позже).
  2. AI Agent — системный промпт: роль, правила, список инструментов, запреты.
  3. Инструменты агента — Call n8n Workflow Tool: каждый воркфлоу А–Д подключён как «инструмент» с понятным описанием и схемой входа. Агент не знает про НП или SQL, он знает «есть инструмент create_ttn(orderId)».
  4. Инструменты только для чтения (KPI, статус заказа, остатки) агент вызывает сам. Инструменты, которые что-то меняют, по умолчанию идут через одобрение.
  5. MCP Server Trigger ✅ (есть в n8n) — тот же набор воркфлоу можно открыть внешнему агенту, например Grok Bot, по протоколу MCP.

Каждое действие пишется одной строкой: время, воркфлоу, кто запустил (агент, расписание, человек), что сделано, ID объекта в Perry, кто одобрил, сколько минут ручной работы заменено. 15.2. Что сделать первым для портфолио

Три воркфлоу, которые Сергей может собрать в локальном n8n против локального Perry API (dotnet run → http://host.docker.internal:5272) и показать на собеседовании. Для каждого — формула «было → стало → часы → деньги».

ПФ-1. Утренний KPI-дайджест в Telegram

Основа — Д1. Работает без изменений в коде Perry.

  1. Schedule Trigger 09:00 → 2. HTTP Request POST /api/dev/admin-login (код) → 3. HTTP Request GET /api/orders/admin?fromUtc=…&toUtc=… с Authorization: Bearer {{token}} → 4. Code: заказы, выручка, statusCounts, сравнение со вчера → 5. OpenAI: 3 вывода → 6. Telegram.

Что показать: живое сообщение в Telegram; экран заказов в админке с теми же цифрами. Было: 30 мин в день открывать админку и считать. Стало: 0. Итого: 15 ч/мес ≈ 3 000 грн/мес ⚠️ на одного руководителя.

ПФ-2. Telegram-бот «Где мой заказ?»

Основа — Г1.

  1. Telegram Trigger → 2. AI Agent (память Simple Memory) с инструментом HTTP Request Tool GET /api/orders/admin?orderId={{номер}} → 3. Code: сверить email, перевести статус → 4. Telegram ответ; 5. ветка IF «не нашёл» → Telegram в чат оператора.

Что показать: диалог с ботом по реальному номеру из «Мои заказы»; честно сказать, что в бою нужен узкий эндпоинт API-2 вместо админского. Итого: ≈ 25 ч/мес ≈ 5 000 грн/мес ⚠️.

ПФ-3. AI-описание товара с одобрением человеком

Основа — Б1. Показывает самое ценное для вакансии: AI + API + человек в контуре.

19.1. По шагам

  1. Заказ. Клиент нажимает Place order на checkout или в мобильном. Perry создаёт заказ с номером вида #AT456BB (OrderService.cs). Чтобы дальше всё работало, на checkout нужны телефон и отделение НП (API-5, G1).
  2. Оплата. Сейчас оплата демонстрационная (G2). В бою провайдер шлёт вебхук «оплачено», и заказ идёт дальше ❓ (вопрос 10).
  3. Резерв на складе. Perry уже проверяет и списывает остаток, на нуле ставит OutOfStock (код). Если остаток стал мал, оркестратор запускает А2 → человек одобряет закупку.
  4. Накладная. Событие order.created попадает к оркестратору. Он запускает А3 (сборочный лист → склад собирает), затем А4 (ТТН через API НП). Нет данных → оператор исправляет.
  5. Уведомления. Номер ТТН сохраняется в заказ и уходит клиенту в Telegram или по email (А4, шаг 9). Письмо о смене статуса Perry шлёт сам (код).
  6. Трекинг. Каждые 2 часа А5 спрашивает НП и двигает статус в Perry. В любой момент клиент может спросить бота.
  7. Доставка. Клиент забирает посылку. Возврат идёт по А6 → оператор одобряет деньги.
  8. Запрос отзыва. Через 3 дня после «получено» клиент получает просьбу оставить отзыв. Новый отзыв проходит AI-модерацию → модератор подтверждает в админке.
  9. Аналитика. Всё, что произошло, попадает в журнал, KPI-дайджест, отчёт маркетинга и алерты.
  10. Маркетинг. Из аналитики рождаются посты, рассылки и напоминания о корзине (В1, В4, В3) → маркетолог одобряет → клиент возвращается и делает новый заказ (шаг 1).

Сколько человека остаётся в этом цикле: собрать коробку, одобрить закупки, возвраты, публикации и спорные отзывы. Всё остальное — набор данных, переписывание и ответы на одни и те же вопросы — делает система. Это и есть те ≈ 362 часа в месяц из раздела 14.
